# Design

## Context

Как CLI 0.1.8, встроенный в `@qwen-code/sdk`, обращается с MCP (проверено по его коду):

- MCP-инструменты называются `mcp__<server>__<tool>` и регистрируются отдельно от встроенных.
  Allowlist `coreTools` (`--core-tools`) действует только на встроенные инструменты
  (`PermissionManager.isToolEnabled`), поэтому `tools:` роли MCP не включает и не выключает.
- `excludeTools` SDK сливается с `permissions.deny` (`getPermissionsDeny`). Для MCP-имён правило
  сопоставляется через `matchesMcpPattern`: точное имя, префикс с `*` (`mcp__*`, `mcp__jira__*`) или
  `mcp__<server>`. Deny-правило не убирает MCP-инструмент из init-списка, но планировщик
  (`isToolEnabled`) отклоняет вызов до исполнения и до `getDefaultPermission`.
- Модели MCP-инструменты в списке `tools` запроса не уходят: они отложены за `tool_search`.
  Вызвать инструмент по имени модель всё равно может.
- Разрешение по умолчанию у MCP-вызова (`DiscoveredMCPToolInvocation.getDefaultPermission`):
  `allow`, если у сервера `trust: true` в доверенном каталоге или у инструмента `readOnlyHint`,
  иначе `ask`. Только `ask` доходит до `canUseTool`, то есть до ACL контроллера.
- `--allowed-mcp-server-names` оставляет только названные серверы. SDK не передаёт пустой список,
  поэтому выключить все серверы им нельзя.
- Init-сообщение сессии содержит `tools` (с MCP) и `mcp_servers: [{name, status}]`.
- Серверы, переданные в `query({ mcpServers })` как SDK-серверы (`createSdkMcpServer`), CLI считает
  доверенными: их инструменты выполняются без `canUseTool`. Серверы с `command` (stdio, как в
  настройках CLI) ведут себя по правилам выше.
- Всё это проверено пробником: CLI из SDK и фейковый OpenAI-эндпоинт, который возвращает вызов
  нужного инструмента.

Мотивация — proposal.md, «Why».

## Goals / Non-Goals

**Goals:**
- MCP-инструмент доступен роли, только если его явно разрешает policy, и это видно в логе ACL.
- У роли без разрешения MCP-инструментов нет совсем, в том числе тех, что CLI выполнил бы без ACL.

**Non-Goals:**
- Конфигурация MCP-серверов из policy (`mcpServers` в `query()`): серверы настраиваются в CLI.
- Разрешения на уровне параметров вызова (какой проект Jira и т. п.).

## Decisions

- **Ключ `roles.<роль>.mcp: string[]` в policy, а не `tools:` frontmatter** (`policy.ts`,
  `.agentflow/policy.yaml`). Полномочия в kit задаёт policy, роль только описывает себя; это
  совпадает с `write` и `shell`. Отсутствие ключа значит `[]`. Шаблоны — glob по имени инструмента
  (`matchesAny`, как у путей); `{change}` и `{acceptance}` в них не раскрываются.
- **Отключение MCP через `excludeTools: ['mcp__*']`** (`roles.ts`, опции `query()`), если `mcp`
  роли пуст или шаг `readOnly`. Deny-правило проверяется раньше разрешения по умолчанию, поэтому
  `trust` и `readOnlyHint` уже ничего не значат. Альтернатива «отклонять в `canUseTool`» не работает: для
  `allow` по умолчанию callback не вызывается.
- **MCP запрещён в шаге «только на чтение»** даже при непустом `mcp`. MCP-инструмент может менять
  внешнюю систему, а шаг уточнений обещает отсутствие побочных эффектов. Если понадобится Jira в
  уточнениях, это отдельное разрешение (вне scope).
- **`allowedMcpServerNames` из шаблонов роли** (`roles.ts`). Сервер берётся из второго сегмента
  `mcp__<server>__…`. Если хоть один шаблон не называет сервер явно (`mcp__*`, `mcp__ji*`), список
  не передаётся и подключаются все серверы CLI. Так роли не видят лишних серверов и инструментов.
- **ACL для MCP** (`decideAcl`): имя с префиксом `mcp__` разрешается, если совпадает с шаблоном
  роли и шаг не `readOnly`. Причина в логе — совпавший шаблон или «нет в roles.<роль>.mcp».
- **Сверка MCP-вызовов после роли** (`roles.ts` собирает имена `tool_use` с `mcp__` в
  `RoleResult.mcpCalls`; `controller.ts`, `callRole` и `callReviewer`). Вызов вне allowlist —
  `Blocked`, как у `checkBoundary`. Это вторая линия для инструментов разрешённого сервера,
  которые CLI выполнил без ACL (`trust`/`readOnlyHint`), когда шаблоны роли точечные.
- **Диагностика** (`roles.ts`, `controller.ts`). В строке «сессия открыта» добавляются MCP-серверы
  со статусом и число MCP-инструментов. При загрузке ролей `mcp__…` из `tools:`, которых не
  покрывает `mcp` policy, дают `log.warn` с ключом policy. Из `coreTools` такие имена убираются: CLI
  на них не смотрит, а в списке они путают.

Проверка mock-прогоном: mock-роли MCP не вызывают, поэтому `run tasks/01-slugify.md --mock
--auto-approve --inject all` в копии kit (`git init`) должен пройти до archive без изменений
поведения. Это проверка, что `mcp: []` по умолчанию ничего не ломает. Поведение MCP проверяется
unit-тестами `decideAcl`, опций сессии и сверки, а на реальном CLI — `npm run smoke` с тестовым
stdio-сервером `tools/agentflow/smoke-mcp-server.mjs`: SDK-серверы для этого не годятся, CLI им
доверяет.

## Risks / Trade-offs

- [Имя сервера с символами вне `[a-zA-Z0-9_.-]` CLI нормализует в `_`] → шаблон пишется по
  фактическому имени инструмента из init-сообщения; README показывает, где его взять (`agentflow
  agents`, строка «сессия открыта»).
- [Точечный шаблон на сервере с `trust: true`] → лишний read-only вызов выполнится, но run уйдёт в
  BLOCKED после роли. README рекомендует шаблоны уровня сервера (`mcp__jira__*`) или `trust: false`.
- [MCP-вызов в обход ACL завершился ошибкой инструмента] → в сверку не попадает: выполненным
  считается вызов с успешным `tool_result`, иначе отказ CLI и ACL было бы не отличить от
  выполнения.
- [Корпоративный CLI отличается от 0.1.8 в обработке `excludeTools` для MCP] → smoke проверяет, что
  инструмент роли без `mcp` не выполнился.

## Migration Plan

Действий не нужно. Чтобы дать роли MCP, добавить в `.agentflow/policy.yaml` целевого репозитория
`roles.<роль>.mcp: ["mcp__<server>__*"]`.
