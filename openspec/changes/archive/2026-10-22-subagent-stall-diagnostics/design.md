# Design

## Context

Мотивация — proposal.md, требования — дельты `specs/pipeline-orchestration`, `specs/role-sessions`,
`specs/human-decisions`. Панель статуса из change `status-panel` уже в коде.

Что есть сейчас:

- `roles.ts/runRole` читает поток `query()`. `log.toolUse` печатает вызов и увеличивает счётчик
  в панели, `tool_result` с `is_error` печатается красной строкой. `log.roleDone` вызывается, только
  если пришёл `result`. При падении CLI панель не узнаёт, что сессия закончилась, пока не придёт
  следующий `spawn`.
- `aclFor` вызывает `decideAcl`, печатает `log.acl` и отвечает модели `agentflow ACL: <reason>`.
  `canUseTool` в SDK 0.1.8 получает имя и вход инструмента, `tool_use_id` в нём нет.
- `отказов ACL` в итоге роли — это `result.permission_denials.length`. CLI кладёт туда и наши
  отказы, и свои (`excludeTools`/`denyAll`, настройки CLI). Элементы списка: `{tool_name, tool_use_id, tool_input}`.
- Таймаута у роли по умолчанию нет (`roleTimeoutMinutes: 0`), таймаута у гейтов нет вовсе.
  Таймаут одного запроса к модели — `qwen.apiTimeoutSeconds` (600 в kit).
- Повторы шага: `callRole`/`callReviewer` в `controller.ts` — серия из `infraRetries + 1`
  попыток, потом `infraExhausted` (диалог «ещё серия / стоп»).
- Вложенный субагент CLI — инструмент `task` (так в типах SDK; в init-списке встречается и
  `agent`). Его сообщения приходят в том же потоке с `parent_tool_use_id` вызова.
- `@inquirer/prompts` 8.7: второй аргумент промпта принимает `{ signal }`. При отмене промпт
  отклоняется с `AbortPromptError`.
- Fault injection решает контроллер (`ctx.inject.take`), mock-роль получает готовый признак через
  `RoleCall`/`TaskMeta`.

## Goals / Non-Goals

**Goals:**
- Отслеживание сессии (текущий шаг, простой, вложенные субагенты, отказы, серия) — отдельный
  класс без ввода-вывода с подставляемыми часами, проверяемый unit-тестом. `runRole` и `runMock`
  пользуются им одинаково.
- Решение о вмешательстве принимает контроллер (`Human.select` с рекомендацией и обоснованием),
  `roles.ts` только сообщает событие и исполняет решение.
- Категория и подсказка ACL — чистая функция от решения ACL и policy.

**Non-Goals:**
- Изменение формата `state.json`. Новые поля появляются только в событиях `events.jsonl`
  (`acl`: `category`, `hint`; новые `stall`, `intervention`, `denials`).
- Отдельный вывод потока вложенного субагента: его сообщения обновляют активность и шаг, лог
  остаётся прежним.

## Decisions

### 1. `SessionTracker` — состояние одной сессии

Новый модуль `tools/agentflow/session-tracker.ts`:

```
class SessionTracker {
  constructor(o: { role; stallMs; denialStreak; now?: () => number })
  event(m: SDKMessage)            // любое сообщение потока: lastEventAt = now
  toolUse(id, name, arg, nested)  // шаг = «→ name arg» с now; task/agent → nested++
  toolResult(id, isError)         // pending--, task/agent → nested--; без pending шаг = «ждёт ответа модели»; успех сбрасывает серию
  acl(decision, tool, target)     // отказ: denials.push, streak++; разрешение: streak = 0
  step(): { label, since }        // для панели и диагноза простоя
  idleMs(), stalled(), streakHit()
  summary(permissionDenials)      // группы отказов: наши по (tool, reason) + CLI-отказы без пары
}
```

Шаг определяется так. Сразу после старта — «ждёт ответа модели». После `tool_use` — последний
незавершённый вызов (при нескольких параллельных — самый ранний). После `tool_result` без
незавершённых вызовов — снова ожидание модели. Сообщение с `parent_tool_use_id` — шаг
«вложенный субагент: <последний его вызов>». Ни шаг, ни время шага не зависят от вывода в лог.

Альтернатива — считать время шага по последней строке лога в `log.ts`. Отказался: лог печатает
и то, что шагом не является (`… размышляет`, текст), и mock-роль тогда разошлась бы с настоящей.

### 2. Сторож простоя и вмешательство

`RoleCall` получает поле `intervene?: (ev: Intervention, signal: AbortSignal) => Promise<'wait' | 'retry' | 'stop' | 'woke'>`.
`runRole` и `runMock` держат `setInterval(1000).unref()`. Когда `tracker.stalled()` или
`tracker.streakHit()` срабатывает и вмешательство ещё не идёт, они:

1. Пишут событие `stall`/`acl-streak` в ledger: роль, шаг, `с HH:MM:SS`, простой или список
   отказов серии. Диагноз в лог печатает `intervene` первой строкой контекста диалога. Контекст
   выводится и под `--auto-approve`, поэтому отдельная строка предупреждения только повторила бы его.
2. Вызывают `intervene` с `AbortController`. В диалоге простоя его `signal` прерывается первым же
   новым сообщением сессии, и тогда `intervene` возвращает `woke`. Диалог серии ACL от сообщений
   не закрывается: роль, упёршаяся в ACL, шлёт отказы непрерывно, и меню закрывалось бы сразу.
   Если сессия закончилась, пока диалог открыт, сторож закрывает его сам, и позднее решение не действует.
3. Исполняют решение. `wait` и `woke` сбрасывают отсчёт простоя или серию. Простой в диагнозе
   по-прежнему считается от последнего события, а не от решения «ждать». `retry` и `stop`
   прерывают сессию через её `abortController`, а `runRole` возвращает
   `{ ok: false, error, intervention: { kind, decision, denials? } }`. При `stop` контроллер
   бросает `Blocked`, `roles.ts` про BLOCKED не знает.

Обработчик `intervene` (`interventionHandler` в `controller.ts`) строит `callRole`/`callReviewer` на каждый вызов.
Рекомендация, тексты диагноза и дополнение промпта — чистые функции в `intervention.ts`:
`controller.ts` при импорте запускает CLI, и unit-тесты не могут его импортировать. В его замыкании живёт
счётчик простоев этого шага: он один на все попытки серии и все серии, поэтому `--auto-approve`
идёт по цепочке «ждать → повторить → стоп» и не зацикливается. Рекомендация:

| Причина | Рекомендуется | Обоснование |
| --- | --- | --- |
| простой №1 | ждать | ответ модели на высоком effort бывает долгим, гейт внутри сессии тоже |
| простой №2 | повторить шаг | сессия молчит второй порог подряд, новая сессия дешевле ожидания |
| простой №3+ | остановить | повтор тоже завис — причина устойчивая (CLI, модель, гейт) |
| серия ACL, есть «не хватает разрешения» | остановить | роли нужен доступ, его даёт только правка policy (ключ в обосновании) |
| серия ACL, все «ожидаемо» | повторить шаг | новая сессия получит список запретов и разрешений в промпте |

Пункты меню: «Ждать дальше», «Прервать сессию и повторить шаг», «Остановить run (BLOCKED, потом resume)».
`retry` засчитывается как неуспешная попытка серии в `callRole`, поэтому после исчерпания
серии открывается обычный `infraExhausted`. Новый тип диалога исчерпания не нужен.

Порог: `limits.stallMinutes` (по умолчанию 15). Под `--mock` порог 2 с, чтобы точку `stall:<роль>`
можно было пройти за секунды. Серия: `limits.aclDenialStreak` (по умолчанию 5). Если
`stallMinutes * 60 <= (qwen.apiTimeoutSeconds || 120)`, при старте run печатается предупреждение.

Альтернативы:
- Прерывать сессию сразу по порогу без диалога. Отклонено: модель на effort max законно думает
  дольше десяти минут, а решение в конвейере — за человеком.
- Ставить по умолчанию `roleTimeoutMinutes`. Отклонено: жёсткий лимит не отличает работающую
  сессию от зависшей, сторож смотрит на активность.

### 3. Диалог во время работающей сессии

`Human.select` получает необязательный `signal` и возвращает `undefined`, если диалог отменили
(`AbortPromptError`). В обёртке `paused()` к `panel.pause()/resume()` добавляется
`log.hold()/log.release()`. Пока лог удержан, `line()` копит строки в буфере, а `emit()` пишет
в `events.jsonl` сразу. После диалога буфер выводится одним блоком. Удержание общее для всех
диалогов, поэтому меню никогда не рвёт параллельный вывод. Сейчас параллельный вывод бывает
только у вмешательства.

Если диалог отменён (`woke`), в лог пишется `сессия ожила после N мин простоя — ждём дальше`.
С `--auto-approve` меню нет: рекомендация выбирается сразу, `signal` не нужен.

### 4. Объяснение отказов ACL

`decideAcl` возвращает ещё `category: 'expected' | 'permission'`, `hint` (для человека) и
`allowed` (что роли разрешено в этой категории, для модели):

| Причина | Категория | Подсказка |
| --- | --- | --- |
| шаг только на чтение | expected | шаг уточнений только читает, действий не нужно |
| вне worktree / нет пути | expected | роль ошиблась путём, действий не нужно |
| запись не по `roles.<r>.write` | permission | добавь glob для `<путь>` в `roles.<r>.write` (`.agentflow/policy.yaml`) |
| путь в `roles.<r>.denyWrite` | expected | путь защищён шаблоном `<glob>`. Если он нужен роли — убери шаблон из `denyWrite` |
| shell не `agentflow-gate <op>` | expected | роли доступны только `agentflow-gate`. Нужна другая команда — оформи операцию в `gates.ops` и добавь в `roles.<r>.shell` |
| операция есть в `gates.ops`, нет в `roles.<r>.shell` | permission | добавь `<op>` в `roles.<r>.shell` |
| операции нет в `gates.ops` | expected | такой операции нет, доступны: `<ops роли>` |
| MCP не по `roles.<r>.mcp` | permission | добавь шаблон `<tool>` в `roles.<r>.mcp` |
| инструмент вне политики | expected | инструмент ролям не выдаётся (`ask_user_question`: вопросы идут через шаг уточнений) |

Модель получает `agentflow ACL: <reason>. Разрешено: <allowed>. Не повторяй этот вызов — обойдись разрешённым.`
Строка `✗ ACL` в логе получает метку категории (`ожидаемо` серым, `не хватает разрешения`
жёлтым) и следующую строку `что делать: <hint>`. Событие `acl` в ledger получает `category` и `hint`.

Сводка в итоге роли. `tracker.summary(result.permission_denials)` сопоставляет отказы CLI с
нашими по имени инструмента и цели: цель из `tool_input` извлекается той же функцией, что
`toolArg`/`decideAcl`. Совпавшие группируются по `(tool, reason)` со счётчиком. Несовпавшие идут
отдельной группой `отклонено CLI мимо ACL контроллера — правило denyAll / excludeTools или
настройки CLI (.gigacode/settings.json)`. `log.roleDone` печатает строку `отказов ACL: N` как
раньше и под ней по строке на группу: `✗ 2× run_shell_command npm test — <reason> · <категория>: <hint>`.
Группа — событие `denials` в ledger. Если `result` не пришёл, сводка строится по нашим отказам.

### 5. Панель: три строки

`status-panel.ts`: `HEIGHT = 3`, `MIN_ROWS` остаётся 10. Новые поля `PanelState`:
`active: { sessions, nested }`, `stallMs`, `activitySince`, а в `PanelAgent` — `step: { label, since }`,
`denials: { count, last? }`.

- Строка 1 — субагент как раньше. Счётчики в конце: `активных 1 (+1 вложенный) · запуск 7 · ролей 5`.
  Без субагента: `⚙ контроллер · активных 0 · запуск 7 · ролей 5`.
- Строка 2 — шаг: `  ↳ → run_shell_command agentflow-gate unit · с 14:02:31 · 09:00`, дальше,
  если были отказы: `· ✗ ACL 3: <последняя причина>`. Длительность шага жёлтая с половины
  порога и красная от порога (`простой 15:02`). Без субагента:
  `  ↳ гейт unit выполняется · с 14:10:02 · 00:41` (`activity` + `activitySince`).
- Строка 3 — контекст прогона как раньше.

`renderPanel(state, width, now)` остаётся чистой функцией и возвращает три строки. Перерисовку
раз в секунду уже делает таймер панели, отдельный таймер для шага не нужен.

Хуки: `log.spawn` — `sessions++`. Новый `log.roleEnd(role)` вызывается из `finally` в `runRole`
и `runMock` при любом исходе: он делает `sessions--`, `nested = 0` и `agent = undefined`.
`log.roleDone` только печатает итог. `log.step/gate/verdict/human` выставляют `activitySince = now`.
Новый `log.gateStart(op)` из `runGates` перед запуском команды выставляет `activity = гейт <op>
выполняется`, строку в лог не печатает. `tracker` передаёт шаг, отказы и вложенных в панель через
`panel.update` при каждом своём изменении.

### 6. Время в строках роли

`log.role(role, text)` печатает `<роль> │ HH:MM:SS <text>`, время серое и локальное. Его же
получают `toolUse`, `acl` и строка `что делать`. Строка `▶ субагент <роль> · HH:MM:SS [модель …]`.
Время берётся в момент печати, а при удержании лога — в момент события, поэтому отложенные
строки сохраняют настоящее время. Строки контроллера (`⚙`, `●`, `◆`) не меняются: события в
`events.jsonl` и так несут `at`.

### 7. Fault injection `stall:<роль>`

`INJECT_ALL` получает `stall:implementer`. `callRole` перед первой попыткой вызывает
`ctx.inject.take(\`stall:${name}\`)` и передаёт `silent: true` в `TaskMeta`. `runMock` с
`silent` после `spawn` ждёт, пока сессию не прервут, и ничего не присылает. Под
`--auto-approve` по порогу 2 с идёт так: простой №1 → ждать, простой №2 → повтор, вторая
попытка без `silent` проходит. Прогон длиннее примерно на 4 с.

### 8. Policy

`policy.ts`: `limits.stallMinutes` (15) и `limits.aclDenialStreak` (5) с дефолтами для
репозиториев, где их нет. `.agentflow/policy.yaml` kit получает оба ключа с комментариями.

### Проверка mock-прогоном

- `npm run agentflow -- run tasks/01-slugify.md --mock --auto-approve --inject all > out.log`:
  run принят. В `out.log` есть `fault injection: stall:implementer`, предупреждение о простое
  implementer с `ждёт ответа модели` и временем, `(--auto-approve) → Ждать дальше`, затем
  `→ Прервать сессию и повторить шаг`, `ошибка шага (простой …) — попытка 1/3` и успешная вторая
  попытка. Строки ролей несут время `HH:MM:SS`. В `events.jsonl` есть события `stall` и
  `intervention`, а у событий `acl` — `category` и `hint`.
- Тот же прогон в TTY: панель в три строки, во время простоя строка шага сначала жёлтая, потом
  красная, счётчик `активных 1`. После `■ implementer завершил` — `активных 0`.
- Без `--auto-approve` в TTY с `--inject stall:implementer`: открывается меню вмешательства,
  выбор «Ждать дальше» возвращает панель. Строки, которые mock напечатал во время меню, выводятся после него.
- Отказы ACL в mock не воспроизводятся: mock-роли пишут только разрешённое. Категории, подсказки,
  серия и сводка проверяются unit-тестами `decideAcl` и `SessionTracker` с подставленными
  `permission_denials`.

## Risks / Trade-offs

- [Сопоставление отказов CLI с нашими по (tool, цель) неточно при одинаковых вызовах] → группы
  считают количество, а не идентичность. Ошибка тут даёт неверное число в группе «отклонено CLI»,
  а не потерянный отказ.
- [Сообщения вложенного субагента приходят не во всех версиях CLI] → тогда вложенный субагент
  виден только как незавершённый вызов `task`/`agent`, а сторож считает его простоем. Диагноз
  при этом называет вызов вложенного субагента, и человек решает «ждать».
- [Удержание лога на время долгого диалога копит строки в памяти] → буфер ограничен 2000 строками.
  Сверх лимита строки отбрасываются с отметкой, полный поток остаётся в `events.jsonl`.
- [Модель всё равно повторяет запрещённый вызов, несмотря на подсказку] → это ловит серия отказов ACL.
- [Третья строка панели отнимает строку лога] → порог `MIN_ROWS = 10` по-прежнему оставляет
  логу не меньше 7 строк. `--no-panel` остаётся.

## Migration Plan

Миграция не нужна. Новые ключи policy имеют дефолты. Старое поведение возвращают
`stallMinutes: 0` и `aclDenialStreak: 0`. Формат `state.json` не меняется, у событий
`events.jsonl` только добавляются поля. Change `status-panel` стоит заархивировать раньше этого.
