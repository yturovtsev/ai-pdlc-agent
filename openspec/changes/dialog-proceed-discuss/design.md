# Design

## Context

- Диалоги решений — `Human.select` (`human.ts`): рекомендуемый вариант первым, `--auto-approve` берёт
  его. Обсуждение есть только у `Human.question`: пункт «Обсудить / уточнить», реплика через `Discuss`,
  переписка в `state.json` у вопроса, лимит `limits.discussTurns`.
- Диалоги с «Остановить run» в `controller.ts`: `infraExhausted` (серия сбоев CLI), `interventionHandler`
  (простой и серия ACL, решение исполняет `Watchdog` в `roles.ts`), `artifactExhausted`, блокер ревью
  артефакта (внутри `artifactLoop`), исчерпание `holisticLoop`, `applyExhausted` (батч и финал). Ещё в
  `artifactGate` и в согласовании спеки, но там первый вариант и так ведёт дальше.
- Сразу `throw new Blocked` по вердикту роли: BLOCKED в `holisticLoop`, `batchLoop`, `runAcceptance`,
  `stageFinal`; спор по находке security/behavior в `applyReview`; `NEEDS_SPEC_CHANGE` в
  `implementWithGates`. Остальные `Blocked` — контроль целостности, они не меняются (proposal, вне scope).
- Waiver уже пишет `status: 'waived'` и `waiver {reason, at, snapshot}` у находки, отчёт показывает
  такие находки в отдельном разделе.
- `openspec archive --yes` проходит при незакрытых задачах: OpenSpec только предупреждает.

## Goals / Non-Goals

**Goals:**
- Один механизм перехода дальше для всех диалогов, без отдельной логики «пропуска» в каждом
  диалоге: диалог знает только текст пункта, петля сама решает, что значит «пройдена».
- Одна реализация обсуждения для вопросов и решений: меню, лимит реплик и запись переписки общие.
- Автопилот без точек inject проходит те же пути, что и сейчас.

**Non-Goals:**
- Переход дальше по одной находке. Снимается весь остаток петли.
- Обсуждение с ролью, которой нет в петле, и выбор роли текстом.
- Отмена перехода дальше: снова пройти петлю можно только новым run.

## Decisions

### 1. Петля, которую можно пройти: стек областей и исключение `PassLoop`

Каждая петля на время работы кладёт в `ctx` область: `{ loop, label, check? }`. Это шаг уточнений,
`artifact:<id>`, `holistic`, `batch:<id>`, `acceptance` и `final`. `label` — текст пункта, например
«считать батч 2 выполненным → батч 3». `check()` возвращает причину недоступности или `undefined`.
Помощник `askHuman` в новом модуле `dialogs.ts` (имя `decide` занято правилами принятия ревью) строит меню любого диалога с «Остановить run». Он
добавляет пункты обсуждения (решение 4), затем «Остановить run», последним — «Всё равно перейти
дальше: <label верхней области>». При выборе последнего пункта он спрашивает причину и бросает
`PassLoop(scope, reason)`. Петля ловит `PassLoop` только своей области и закрывается (решение 2).
Внешние петли его пропускают.

`PassLoop`, стек и `askHuman` лежат в `dialogs.ts`, а не в `controller.ts`: контроллер при импорте
запускает `main()`, а их проверяют unit-тесты. `infraExhausted` и `interventionHandler` вызываются глубоко внутри `callRole`. Стек нужен, чтобы
они без лишних параметров знали, какую петлю пройти. Исключение доходит до петли через `callRole`,
`callReviewer` и `implementWithGates`: они его не ловят.

Реплика обсуждения (вопроса или решения) кладёт свою область `reply`. `PassLoop` этой области
означает «ответа нет»: меню показывается снова, переписка не меняется (спека, требование «Всё равно
перейти дальше»). Без этого переход дальше из диалога простоя реплики прошёл бы петлю, в которой
открыт вопрос.

Альтернативы: возвращать из диалогов ключ `proceed` и обрабатывать его в каждом месте вызова.
Это шесть копий одной логики, а для `callRole` пришлось бы протаскивать результат через три уровня.
Ещё вариант — флаг в `state.json` и `resume`, как ручной обход: он не работает без остановки run.

### 2. Что значит «пройдена» для каждой петли

Перед закрытием петли открытые блокирующие находки её шага получают waiver с причиной и текущим
snapshot (у батча и финала — snapshot кода последнего ревью или текущий HEAD, если ревью не было).
Затем в `state.json` пишутся решение `proceed` и запись в `proceeded[]`.

| Петля | Что делается | Дальше |
| --- | --- | --- |
| уточнения | вопросов нет | фаза спеки |
| `artifact:<id>` | `status: accepted`, snapshot текущей редакции, `passedBy: 'human'` | следующий артефакт (ревью человеком не открывается) |
| `holistic` | `holisticPassed`, digest текущего пакета | согласование спеки |
| `batch:<id>` | сверка ACL implementer, коммит worktree, `status: done`, `passedBy: 'human'`, галочки не ставятся | следующий батч |
| `acceptance` | сверка ACL acceptance-tester, коммит, `acceptance.status: PASSED_BY_HUMAN` | финал |
| `final` | коммит worktree, `final.status: PASSED_BY_HUMAN`, traceability пустая | отчёт приёмки |

Сверка ACL и коммит нужны, потому что переход дальше может прервать роль на середине записи. Запись
вне ACL — нарушение целостности, и оно переводит run в BLOCKED, как сейчас.

### 3. Недоступный пункт

У `Option` появляется `disabled?: string`, и `PromptIO.select` передаёт его в inquirer: у
`@inquirer/select` есть `disabled: boolean | string` у варианта. Пункт показан серым с причиной, курсор
его пропускает. Область артефакта задаёт `check` через `validateArtifact`: если есть находки
валидатора, пункт недоступен. `check` вызывается при каждом показе меню, после «Исправлю сам» результат
может измениться. Автопилот недоступный пункт не выбирает даже по точке `proceed:`: точка тогда
не срабатывает.

### 4. Обсуждение решения

`Human.select` получает необязательный `discuss: DecisionDiscuss`: роли-собеседники, переписка,
лимит, `onTurn`, `autoMessage`. Для каждой роли добавляется пункт «Обсудить с <роль>…» перед
«Остановить run». Цикл «реплика → ответ → снова меню» и диалог лимита — те же, что у `question`,
поэтому они выносятся в общий метод. `DiscussTurn` получает поле `role`: в одном диалоге могут
говорить две роли.

Собеседники по диалогу: артефакт и сквозное ревью — spec-reviewer и spec-author; батч, финал и
`NEEDS_SPEC_CHANGE` — code-reviewer и implementer; acceptance — acceptance-tester; спор по находке —
ревьюер и автор петли. В диалогах сбоя CLI и вмешательства собеседников нет.

Реплика — одна сессия только на чтение без серии повторов, как у вопроса. Промпт
`decisionDiscussPrompt` (`context-builder.ts`): заголовок, контекст диалога (находки), варианты с
рекомендацией и обоснованием, файлы петли (артефакт, diff батча или финала, отчёт acceptance),
переписка, новая реплика. Ответ — текст или JSON `{answer}` (`parseDiscussReply` без вариантов): роль
варианты не меняет. Мета вызова — `kind: 'discuss-decision'`.

Переписка хранится в `state.json` в `dialogs[<id>]`. Id — гейт решения и порядковый номер его показа
(`exhausted:batch 2#1`), чтобы повторное исчерпание не наследовало старый разговор. В решение пишется
«обсуждение: N реплик». Если выбран вариант, продолжающий петлю («ещё раунд», «указание», «новый
implementer», «дать контекст»), переписка уходит автору в находке человека, как у вопроса по артефакту.

Альтернатива — отдельный метод `Human.decide` рядом с `select`. Получились бы два меню с одинаковым
поведением курсора и рекомендации. Расширение `select` сохраняет одно меню.

### 5. Диалог блокера

Помощник `blocker` (`dialogs.ts`, поверх `askHuman`) заменяет `throw new Blocked` по вердикту
роли. Варианты: «Дать недостающий контекст и повторить шаг», обсуждение, «Остановить run», переход
дальше. Рекомендуется «Остановить run», поэтому автопилот ведёт себя как сейчас: run в BLOCKED с той
же причиной. У блокера ревью артефакта остаётся рекомендация «дать контекст». Его диалог получает
обсуждение и переход дальше, а «Исправлю сам» остаётся.

«Дать контекст» добавляет текст в `intent.clarifications`: так его видят все роли. Дальше —
следующий раунд петли с находкой человека:

| Блокер | Повтор |
| --- | --- |
| сквозное ревью BLOCKED | следующий раунд сквозного ревью |
| батч BLOCKED, `needsHuman` | раунд батча: implementer с находкой человека, гейты, ревью |
| `NEEDS_SPEC_CHANGE` | implementer снова в том же раунде с находкой человека |
| acceptance BLOCKED | acceptance-tester снова с находкой человека |
| финал BLOCKED | раунд исправлений финала по находке человека, затем гейты и ревью |
| спор security/behavior | находка остаётся open, автор получает решение человека следующим раундом |

У спора вариант называется «Решить спор указанием и продолжить»: человек пишет, кто прав.

### 6. Вмешательство и переход дальше

`InterventionChoice` получает `proceed`. Причину спрашивает `interventionHandler` сразу после выбора,
пока сессия ещё работает: потом спрашивать некому. `Watchdog` прерывает сессию, как при `stop`, а
`afterIntervention` бросает `PassLoop` с этой причиной. Если сессия ожила, пока человек вводил
причину, решение всё равно исполняется: выбор уже сделан.

### 7. Сквозное ревью: waiver и переход дальше

В диалоге исчерпания сквозного ревью остаются оба пункта: waiver может быть рекомендован (автор
оспорил всё), а переход дальше — нет. Итог у них одинаковый. Убрать waiver нельзя: требование
«Рекомендация по ситуации» опирается на него. Объединять их в один пункт тоже нельзя: последний
пункт никогда не рекомендуется.

### 8. Отчёт приёмки и диалог приёмки

`report.ts`: раздел «Пройдено решением человека» с петлёй, причиной, временем и id снятых находок.
У финала без трассировки уже есть строка «финальное ревью не пройдено». `stageHumanAcceptance`
берёт контекст и обоснование из `final.status`: при `PASSED_BY_HUMAN` пишется «финальное ревью
пройдено решением человека: <причина>», а не «финальное ревью PASS».

### 9. Автопилот и точки inject

Последний пункт не может быть `recommended`: `askHuman` проверяет это и падает с ошибкой разработки.
Точки (`inject.ts`):
- `proceed:<петля>` — в первом диалоге с этим пунктом в области этой петли автопилот выбирает его с
  причиной «fault injection».
- `blocked:<петля>` — первое ревью петли превращается в BLOCKED (по образцу `injectRevise`), у
  acceptance — ответ acceptance-tester.
- `discuss-dialog` — в первом диалоге исчерпания автопилот задаёт реплику первому собеседнику, затем
  выбирает рекомендацию.

В `INJECT_ALL` входит только `discuss-dialog`: на `artifact-stuck:specs` он даёт реплику
spec-reviewer. Mock-роль на `discuss-decision` отвечает строкой с текстом реплики.

### Модули и проверка

Новый `dialogs.ts`. Меняются `human.ts`, `controller.ts`, `context-builder.ts`, `intervention.ts`, `roles.ts`, `state.ts`,
`report.ts`, `mock.ts`, `inject.ts`, тесты в `agentflow.test.ts`, README и AGENTS.md.

Mock-прогоны в копии kit:
- `--auto-approve --inject all` — как раньше, плюс реплика в диалоге исчерпания specs.
- `--auto-approve --inject blocked:final,proceed:final` — change принят, в `ACCEPTANCE.md` есть раздел
  «Пройдено решением человека».
- `--auto-approve --inject blocked:batch:1` — BLOCKED, затем `resume` доводит run до конца.
- `--auto-approve --inject stall:implementer,proceed:batch:1` — диалог простоя, батч 1 пройден
  решением человека, батч 2 идёт обычно.
- `--auto-approve --inject artifact-stuck:specs,proceed:artifact:specs` — specs принят как есть,
  ревью человеком для него нет.

## Risks / Trade-offs

- [`PassLoop` пройдёт через `try/finally`, который ждёт только `Blocked`] → все места, где ловится
  ошибка роли (`catch` в `runRole` и разборе ответа ревьюера), передают `PassLoop` дальше. Unit-тест
  проходит через `callRole` → `infraExhausted` → петлю.
- [Переход дальше прервал роль на середине записи файла] → сверка ACL и коммит worktree перед
  закрытием батча и acceptance. Артефакт с битым содержимым ловит `validateArtifact`, и пункт
  недоступен.
- [Человек случайно прошёл петлю] → причина спрашивается всегда, переход виден в отчёте и в
  `state.json`. Отменить его нельзя (Non-Goals).
- [Батч без галочек мешает archive] → `openspec archive --yes` их пропускает. Это видно по
  предупреждению OpenSpec в логе archive.
- [Длинное меню: восемь-девять пунктов в исчерпании батча] → `pageSize` уже не меньше числа
  пунктов. Обсуждение и переход дальше стоят в конце, обычные варианты остаются наверху.

## Migration Plan

- `discuss-question` и `expand-thinking` не архивированы. В `human-decisions` этот change меняет
  другие требования, чем `discuss-question` («Диалог выбора» не трогается), а в `pipeline-orchestration`
  — только «Остановка в BLOCKED». Порядок архивирования не важен.
- Старые `state.json` без `proceeded` и `dialogs` читаются как пустые: `resume` работает.
- Откат — revert коммита: новые поля состояния старый код игнорирует.
