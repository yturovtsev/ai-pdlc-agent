# agent-pdlc — конвейер spec-driven разработки на Qwen Code

Реализация документа «Конвейер spec-driven разработки на Qwen Code — финальная конфигурация».
Оркестратор — детерминированный контроллер на TypeScript (`tools/agentflow/controller.ts`).
Пять ролей-субагентов запускаются как отдельные сессии `query()` из `@qwen-code/sdk@0.1.8`
через корпоративный CLI. Роли только предлагают артефакты, код и вердикты; переходы, гейты,
git и решения о прохождении принимает контроллер.

| Роль | Модель (`/model`) | effort | Что делает |
| --- | --- | --- | --- |
| spec-author | `qwen3.8-flash` | xhigh | пишет один артефакт OpenSpec за вызов |
| spec-reviewer | `deepseek-flash` | max | ревью артефакта и сквозное ревью, только чтение |
| implementer | `deepseek-flash` | max | один task batch: тест из сценария, затем код |
| code-reviewer | `glm-5.3-flash` | max | ревью батча и финальное ревью трассировки, только чтение |
| acceptance-tester | `qwen3.8-flash` | xhigh | e2e-тесты по сценариям спеки и evidence |

## 1. Перенос на корпоративную машину

Скопируй каталог целиком, **кроме** `node_modules/` и `.agentflow-runs/`. Потом:

```bash
cd agent-pdlc
npm install                      # Node >= 22.13; @qwen-code/sdk 0.1.8, @fission-ai/openspec 1.14.0
git init && git add -A && git commit -m "agentflow: init"   # контроллер работает в git worktree
```

## Запуск в других репозиториях

Этот репозиторий — **kit**: код контроллера, роли, рубрики, policy по умолчанию и демо-проект.
Конвейер работает в любом локальном git-репозитории, из которого его запустили, и использует
**OpenSpec этого репозитория как есть**: схему из `openspec/config.yaml` (или `.openspec.yaml`
конкретного change), её артефакты, существующие changes, файл задач из `apply.tracks` схемы и
версию `openspec` из `node_modules` репозитория, если она там установлена. Если этот CLI (или CLI kit)
схему не видит, берётся `openspec` из PATH, который её видит, — так подхватываются встроенные схемы
корпоративной сборки. Схемы из `openspec/schemas/` переносятся в worktree, даже если они в `.gitignore`;
если схему не видит ни один CLI, run останавливается до создания change со списком того, что видит каждый.

```bash
# один раз, в kit
npm install && npm link          # глобальная команда agentflow (или: alias agentflow="node <kit>/tools/agentflow/bin/agentflow.mjs")

# в целевом репозитории
cd ~/work/other-repo
agentflow init                   # .agentflow/policy.yaml (гейты проекта), .gitignore; существующий openspec/ не трогает,
                                 # если его нет — openspec init со схемой по умолчанию (--agentflow-schema добавит схему kit)
#   проверь gates.ops и acceptance в .agentflow/policy.yaml, закоммить .agentflow и .gitignore
agentflow smoke                  # CLI, модели, ACL — в этом репозитории
agentflow changes                # changes репозитория: схема, задачи, прогоны
agentflow run --change <id>      # довести существующий change
agentflow run intent.md          # новый change по intent (схема — по умолчанию репозитория)
```

| Что | Откуда берётся |
| --- | --- |
| схема, артефакты, changes, specs | `openspec/` целевого репозитория |
| `openspec` CLI | `node_modules/.bin/openspec` репозитория, иначе kit |
| гейты (`lint`, `unit`, `e2e`) | `gates.ops` в `.agentflow/policy.yaml` репозитория — команды проекта |
| остальная policy | policy kit + `.agentflow/policy.yaml` репозитория (объекты сливаются, списки заменяются) |
| роли | `.agentflow/agents/<роль>.md` репозитория, иначе `.qwen/agents/` kit |
| рубрики | `.agentflow/rubrics/<id артефакта>.md` репозитория, иначе kit; для артефакта без рубрики — `artifact.md` |
| прогоны | `.agentflow-runs/` в репозитории (в git — только `ACCEPTANCE.md`) |

**Существующий change.** Незакоммиченное состояние `openspec/` (сам change, config, схемы)
переносится в worktree. Уже написанные артефакты сначала идут на ревью (spec-author их не
переписывает), недостающие пишет spec-author, уточнение intent пропускается. Задачи, отмеченные
`[x]`, считаются выполненными; принятый батч отмечается в файле задач так же — как принято в OpenSpec.

**Схема без test-plan** (например, `spec-driven`): acceptance-tester строит проверки из сценариев specs.

Роли вызывают гейты одинаково в любом репозитории — `agentflow-gate <операция>`; контроллер кладёт
эту команду в PATH сессий и передаёт ей команды из `gates.ops`. Worktree лежит внутри репозитория,
поэтому `node_modules` основного дерева находятся автоматически. Если инструменты проекта сканируют
всё дерево (tsc `include`, jest), добавь им в исключения `.agentflow-runs/`.

## 2. Настройка (два места)

1. **CLI.** В `.agentflow/policy.yaml` → `qwen.executable` — имя корпоративного CLI в PATH или
   абсолютный путь (по умолчанию `qwen`). Можно перекрыть без правки файла:
   `export AGENTFLOW_QWEN_CLI=/path/to/qwen`.
2. **Модели.** В `.qwen/agents/*.md` поле `model:` — id ровно как в списке `/model` корпоративного
   CLI. Ни route, ни ключей, ни `~/.qwen/settings.json` настраивать не нужно.

Effort берётся из поля `effort:` файла роли и передаётся в сессию через `query({ effort })` —
SDK 0.1.8 это поддерживает. Если модель или шлюз отвечают ошибкой на поле reasoning,
поставь `qwen.effortViaSdk: false`.

Один запрос к модели CLI ждёт 120 с, а на effort `max` ответ бывает дольше. Поэтому kit поднимает таймаут
до `qwen.apiTimeoutSeconds: 600`: значение уходит в сессию как `QWEN_CODE_API_TIMEOUT_MS`, `0` оставляет
дефолт CLI. Сбой API (таймаут, обрыв, 4xx/5xx) CLI отдаёт текстом `[API Error: …]` в успешном ответе;
контроллер считает это ошибкой шага и повторяет его новой сессией.

Зависшую сессию ловит сторож: `limits.stallMinutes` (по умолчанию 15) минут без единого сообщения от
сессии — диагноз в логе и диалог вмешательства, `0` выключает. Порог должен быть больше
`qwen.apiTimeoutSeconds`, иначе сторож сработает раньше таймаута запроса; при старте run об этом
предупреждение. `limits.aclDenialStreak` (по умолчанию 5, `0` — выключено) — столько отказов ACL
подряд открывают тот же диалог: роль упирается в запрет. `limits.discussTurns` (по умолчанию 5) —
столько реплик обсуждения одного вопроса до диалога «продолжить или вернуться к выбору», `0` — без него.

**MCP-инструменты роли.** Серверы настраиваются в самом CLI (для gigacode — `.gigacode/settings.json`
или пользовательские настройки), а разрешает их роли только policy. Перечислить `mcp__…` в `tools:`
файла роли недостаточно: CLI на этот список для MCP не смотрит, контроллер при старте предупредит.

```yaml
# .agentflow/policy.yaml
roles:
  spec-author:
    mcp: ["mcp__jira__*"]        # mcp__<server>__<tool>, * допустим; нет ключа или [] — MCP запрещён
```

- Роль без `mcp` и любой шаг только на чтение (уточнения) не могут выполнить ни одного
  MCP-инструмента: CLI отклоняет вызов по правилу `mcp__*`, даже если у сервера `trust: true` или
  у инструмента `readOnlyHint`.
- Роль с `mcp` подключает только серверы, названные в шаблонах (`mcp__jira__…` → `jira`).
  Шаблон без явного сервера (`mcp__*`) подключает все серверы CLI.
- Инструменты, на которые CLI спрашивает разрешение, проходят ACL (`✓/✗ ACL mcp__…`). Инструменты
  с `readOnlyHint` и с сервера `trust: true` CLI выполняет сам, поэтому после роли контроллер сверяет
  выполненные MCP-вызовы с `mcp`, и вызов вне списка переводит run в BLOCKED. Чтобы этого не было,
  разрешай сервер целиком (`mcp__jira__*`) или ставь серверу `trust: false`.
- Имя инструмента и статус серверов видны в строке «сессия открыта» (`MCP: jira connected,
  инструментов 3`) и в init-сообщении в `events.jsonl`.

## 3. Проверка по шагам

```bash
npm run test:agentflow     # офлайн: контракт ревью, правила принятия, ACL, digest — без моделей
npm run agentflow -- run tasks/01-slugify.md --mock --auto-approve --inject all
                           # весь конвейер на mock-ролях: все петли, гейты, git, archive — без моделей
npm run smoke              # корпоративный CLI: модели из /model, effort, tool calls в thinking mode,
                           # ревьюер не пишет, ACL implementer, resume, MCP по policy
```

В kit команды доступны и как `npm run agentflow -- <команда>` / `npm run smoke`, в любом репозитории —
как `agentflow <команда>` / `agentflow smoke`.

Если smoke пишет `No auth type is selected`, укажи `qwen.authType` в policy (тип из настроек CLI,
обычно `openai`). Результат smoke — в `.agentflow-runs/smoke-*/smoke.json`.

## 4. Боевой прогон

```bash
npm run agentflow -- run tasks/01-slugify.md                 # интерактивно: уточнения, согласование, приёмка
npm run agentflow -- run tasks/01-slugify.md --inject all    # то же, но каждая петля принудительно проходит REVISE
npm run agentflow -- run tasks/01-slugify.md --auto-until-review   # без участия до приёмки: run ждёт тебя на «Принять change?»
npm run agentflow -- run tasks/03-incomplete.md              # неполный intent: ожидаются вопросы человеку или BLOCKED, а не догадки
npm run agentflow -- run "Добавь функцию truncate(text, n)" --change add-truncate
npm run agentflow -- status [<run-id>]                       # состояние и сводка пройденных петель
npm run agentflow -- agents [<run-id>]                       # список субагентов: роль, сессия, модель из ответа API
npm run agentflow -- resume <run-id>                         # продолжить после BLOCKED, сбоя или kill; приёмка запаркованного run
```

### Настройки run

`agentflow run` в интерактивном терминале перед стартом показывает меню с галочками (пробел —
отметить, Enter — запуск, под меню — подсказка к подсвеченному пункту):

- пять ролей — spec-author отмечен серым, это обязательная роль;
- «Уточнение intent» (`--no-clarify` снимает галочку);
- «Автопилот» (`--auto-approve`) и «Автопилот до приёмки» (`--auto-until-review`) — вместе не
  выбираются: меню не подтвердится, пока отмечены оба;
- «Панель статуса» (`--no-panel`) и «Мышь» (`--no-mouse`) — только на этот запуск, `resume` берёт их
  из своих флагов; при `AGENTFLOW_NO_PANEL=1` или `AGENTFLOW_NO_MOUSE=1` пункт недоступен.

Выключенная роль — её шаг пропускается:

- **spec-reviewer** — артефакт после детерминированной валидации OpenSpec сразу идёт на твоё ревью,
  сквозного ревью нет, freeze его не требует;
- **implementer** — run только со спекой: завершается на freeze («Заморозить и завершить run»),
  apply, acceptance, финала и archive нет; code-reviewer и acceptance-tester выключаются вместе с ним.
  Спека закоммичена в ветку, change остаётся активным: код — после `git merge` ветки командой
  `agentflow run --change <id>` (готовые артефакты снова пройдут ревью). С `--auto-until-review` run
  паркуется на «Принять спеку?»;
- **code-reviewer** — батч принимается по зелёным гейтам, финал — только полные гейты (красные
  исправляет implementer, после лимита — диалог исчерпания);
- **acceptance-tester** — этапа acceptance нет, находки финала исправляет implementer.

Без TTY, с `--auto-approve`, `--auto-until-review` или с `--skip-roles <роль,роль>` меню нет: настройки берутся из флагов
(`--no-clarify`, `--auto-approve`, `--skip-roles code-reviewer,acceptance-tester`, `--skip-roles implementer`
для одной спеки). spec-author или неизвестную роль в `--skip-roles` run отклоняет до создания ветки.
Настройки пишутся в `state.json`, `resume` их сохраняет; пропущенные петли в сводке — `SKIPPED`, в
`ACCEPTANCE.md` — раздел «Настройки прогона». Точки `--inject` выключенной роли (`batch-revise`,
`final-revise`, `blocked:final` без code-reviewer и т. п.) не срабатывают.

### Без участия до приёмки: `--auto-until-review`

Прогон, который ты проверишь в конце (например, на ночь): конвейер сам пишет спеку и код и
останавливается на приёмке change.

- **До приёмки решает автопилот** — как `--auto-approve`: уточнения intent и вопросы автора, ревью
  каждого артефакта, freeze, диалоги исчерпания, вмешательство, блокеры. В логе у таких решений
  `(--auto-until-review) →`. Меню настроек run с флагом не показывается; в меню режим — галочка «Автопилот до приёмки».
- **Блокирующие находки не снимаются.** Waiver и «Всё равно перейти дальше» автопилот режима не
  выбирает никогда, даже по точке `--inject proceed:<петля>` (в логе — что переход пропущен). Если
  рекомендован waiver (автор оспорил все находки, сквозное ревью повторяет те же), берётся ещё раунд
  исправлений; на третьем исчерпании рекомендация «Остановить» — run в BLOCKED. Minor и nit, как
  всегда, только в журнал.
- **Парковка.** Дойдя до «Принять change?», run пишет `ACCEPTANCE.md`, получает статус
  `awaiting-review` и завершается с кодом 0 — и в TTY, и без него. В конце лога — отчёт, worktree
  с кодом для ручной проверки, ветка и `agentflow resume <run-id>`. Resume сразу открывает
  «Принять change?» (роли не запускаются); без TTY run остаётся в `awaiting-review`, код 2.
- **Решения переходят к тебе** после парковки или остановки в BLOCKED: время и причина — в
  `state.json` (`handover`), и все следующие решения этого run, в том числе после resume, — твои.
  После сбоя контроллера или kill (`--inject kill-after:<этап>`) resume продолжает с автопилотом.
- **Отчёт.** В `ACCEPTANCE.md` раздел «Режим прогона»: число решений автопилота, когда и почему
  решения перешли к тебе, открытые critical/major, waiver и переходы дальше (у запаркованного run — 0).

С `--auto-approve` флаг несовместим: run не стартует. `--auto-approve` по-прежнему решает всё,
включая приёмку, archive и рекомендованный waiver.

### Где решаешь ты

Все решения — выбор стрелками ↑↓ и Enter. Рекомендуемый вариант стоит первым, помечен `★` и
подсвечен, под меню — его обоснование. `--auto-approve` выбирает рекомендуемое за тебя.

1. **Уточнения intent** — вопросы spec-author с вариантами ответа. В меню вопроса, кроме вариантов
   и «Свой ответ…», есть «Обсудить / уточнить…»: пишешь вопрос или сомнение, spec-author отвечает
   в новой сессии только на чтение (видит intent, вопрос, варианты, артефакт и всю переписку), и
   меню вопроса появляется снова. По ходу роль может уточнить варианты и рекомендацию — в логе
   «варианты обновлены». Переписка уходит автору вместе с выбранным ответом и сохраняется в
   `state.json`; сбой реплики только возвращает в меню. `--auto-approve` обсуждение не открывает.
2. **Твоё ревью каждого артефакта.** spec-author и spec-reviewer доводят артефакт до PASS, затем
   контроллер задаёт отложенные вопросы по нему (с тем же «Обсудить») и предлагает: принять и перейти к следующему,
   вернуть автору с замечанием, исправить самому (ревьюер перепроверит), показать артефакт, остановить.
3. **Лимит автоматических раундов исчерпан** (3 в артефакте, сквозном ревью, батче; 2 исправления
   в финале) — вместо обрыва диалог: ещё раунд, указание автору/implementer, исправлю сам, новый
   implementer, снять находки с причиной (waiver, только в спеке), вернуться к спеке, остановить.
   Рекомендация зависит от ситуации: те же находки повторяются → указание; находки меняются →
   ещё раунд; автор оспорил всё → waiver; гейты красные → свежий implementer. Ниже вариантов —
   «Обсудить с <ревьюер>…» и «Обсудить с <автор>…» (в спеке spec-reviewer и spec-author): реплика
   уходит роли в новой сессии только на чтение, роль видит находки, варианты и всю переписку по этому
   диалогу, после ответа меню то же. Переписка сохраняется в `state.json` (`dialogs`), число реплик —
   в решении, а если выбрано продолжение петли, переписку получает автор следующего раунда.
4. **Freeze** — проходит, только если каждый артефакт принят тобой на текущей редакции (или его
   находки сняты waiver), сквозное ревью PASS и `openspec validate --strict` чист. Правка уже
   принятого артефакта отправляет его и всё ниже по графу на повторное ревью.
5. **Приёмка** — принять (→ `openspec archive`) или отклонить.
6. **Вмешательство в работающую сессию** — при простое или серии отказов ACL: ждать дальше,
   прервать сессию и повторить шаг, остановить run (BLOCKED, потом resume). При простое
   рекомендуется сначала ждать, на втором простое шага — повтор, дальше — стоп, поэтому
   `--auto-approve` не ждёт вечно. При серии отказов: если роли не хватает разрешения — стоп и правка
   policy, иначе повтор; новая сессия получает в промпте отклонённые вызовы и то, что разрешено.
   Пока меню открыто, сессия продолжает работать, её строки лога выводятся после ответа. Если сессия
   ожила, меню простоя закрывается само. Четвёртый пункт — «Всё равно перейти дальше»: сессия
   прерывается, петля, в которой она работала, засчитывается решением человека (см. ниже). В реплике
   обсуждения он только возвращает в меню вопроса или решения без ответа роли.

**«Всё равно перейти дальше».** В каждом диалоге, где можно остановить run, предпоследний пункт —
«Остановить run», последний — «Всё равно перейти дальше: <что произойдёт>». Он спрашивает причину
(Enter — текст по умолчанию) и засчитывает текущую петлю решением человека: уточнения intent
пропускаются, артефакт принимается на текущей редакции без твоего ревью (отложенные вопросы по нему
зададут при согласовании), сквозное ревью считается пройденным, батч — выполненным (его задачи в
файле задач остаются неотмеченными, `openspec archive --yes` их пропускает), acceptance — пройденным,
а в финале пункт называется «Принять без финального ревью → отчёт приёмки». Правки роли, прерванной на
середине, сверяются с её ACL и коммитятся. Незакрытые находки петли снимаются с этой причиной, в
`ACCEPTANCE.md` появляется раздел «Пройдено решением человека», а диалог «Принять change?» пишет, что
финал или acceptance пройдены решением человека, а не PASS. Пока у артефакта есть ошибки `openspec validate --strict`, пункт виден, но
недоступен: без чистой валидации не пройдут freeze и archive. Рекомендацией этот пункт не бывает,
`--auto-approve` его не выбирает.

Waiver, переходы дальше (`proceeded`) и все решения пишутся в `state.json` (`decisions`) и в `ACCEPTANCE.md`.

### Что видно в консоли

```
┌─ петля «артефакт proposal» · раунд 1/3
│ ▶ субагент spec-author · 14:02:10 [модель qwen3.8-flash · effort xhigh · новая сессия 54c7b088]
│   spec-author │ 14:02:31 → read_file src/strings.js
│   spec-author │ 14:03:05 ✓ ACL write_file openspec/changes/add-slugify/proposal.md
│ ■ spec-author завершил · 7 ходов · 41 с · модель из ответа API: qwen3.8-flash
│ ⚙ детерминированная валидация пройдена (файлы, openspec status/validate, формат)
│ ⚙ snapshot артефакта 5cd34c3fd84e
│ ▶ субагент spec-reviewer [модель deepseek-flash · effort max · новая сессия cd7b08a4]
│ ◆ вердикт REVISE · critical 0 · major 1 · minor 0 · nit 0 → назад к spec-author, раунд 2
└─ REVISE
```

`▶` — запуск субагента (время старта, модель, effort, новая или продолженная сессия), `→` — вызов
инструмента, `✓/✗ ACL` — решение контроллера по записи, shell и MCP, `●` — гейт, `◆` — вердикт и куда
дальше, `⚡` — fault injection. В строках роли после её имени — время, когда пришло событие: по нему
видно, с какого момента роль на этом шаге. В конце печатается сводка петель; она же есть в `ACCEPTANCE.md`.

**Отказы ACL.** У каждого отказа — категория и что делать:

```
│   implementer │ 14:05:12 ✗ ACL run_shell_command npm test — разрешена только команда agentflow-gate <операция> · ожидаемо
│   implementer │ 14:05:12   что делать: роль должна вызывать agentflow-gate; если нужна другая команда — оформи её операцией в gates.ops и добавь в roles.implementer.shell
│ ■ implementer завершил · 12 ходов · 310 с · модель из ответа API: deepseek-flash · отказов ACL: 3
│   implementer │ ✗ 2× run_shell_command npm test — разрешена только команда agentflow-gate <операция> · ожидаемо
│   implementer │   что делать: …
│   implementer │ ✗ 1× run_shell_command git status — отклонено CLI мимо ACL контроллера · отклонено CLI
│   implementer │   что делать: вызов отклонил сам CLI: правило denyAll или excludeTools из policy либо настройки CLI …
```

- `ожидаемо` — запрет задуман (шаг только на чтение, shell-команда вместо `agentflow-gate`, защищённый
  путь `denyWrite`, инструмент вне политики), роль обойдётся сама, действий не нужно.
- `не хватает разрешения` — роли может быть нужен доступ: подсказка называет ключ policy
  (`roles.<роль>.write`, `.shell`, `.mcp`) и что в него добавить.
- `отклонено CLI` — вызов отклонил сам CLI (`denyAll`, `excludeTools`, настройки CLI), контроллер
  его не видел; в итоге роли он есть, потому что CLI считает его в `permission_denials`.

Модель в ответе на отказ получает причину, то, что ей разрешено, и просьбу не повторять вызов.

Внизу терминала во время `run` и `resume` закреплена панель статуса, лог прокручивается над ней:

```
▶ implementer 02:14 · батч 1 · deepseek-flash · effort max · новая сессия · инстр. 12 · активных 1 · запуск 7 · ролей 5
  ↳ → run_shell_command agentflow-gate unit · с 14:02:31 · 01:05 · ✗ ACL 1: run_shell_command npm test — …
⏱ 18:40 · петля «task batch 1 «Функция slugify»» 1/3 · ФАЗА APPLY · change add-slugify · run 20261020-…
```

В первой строке — текущий субагент: сколько он работает (время растёт каждую секунду, даже когда
модель молчит), над чем работает (`пишет design.md`, `ревью design`, `сквозное ревью change`, `батч 2`,
`ревью батча 2`, `acceptance-тесты`, `финальное ревью`), модель, effort, новая или продолженная сессия, сколько вызвал инструментов, номер
запуска в run (resume продолжает счёт) и число ролей. `активных` — открытые сессии конвейера, в скобках
вложенные субагенты CLI (`task`/`agent`), ещё не вернувшие результат. Пока субагента нет, в этой
строке `⚙ контроллер`.

Вторая строка — текущий шаг: что сессия делает сейчас (`ждёт ответа модели`, `→ <инструмент> <аргумент>`,
`вложенный субагент: …`), с какого времени и сколько он длится. С половины порога простоя
(`limits.stallMinutes`) время жёлтое, от порога — красное `простой мм:сс`. Дальше — отказы ACL сессии
и последняя причина. Без субагента — последний шаг контроллера и его начало: гейт (`гейт unit
выполняется` — с момента запуска), вердикт, решение человека. Третья строка — время команды, петля
с раундом, этап, change и run id. Длинные строки обрезаются по ширине окна.

На время диалога панель убирается, после ответа появляется снова. Она не включается без TTY
(вывод в файл или pipe), в окне ниже 10 строк или уже 40 колонок, с `--no-panel` и при
`AGENTFLOW_NO_PANEL=1`. При выходе, включая Ctrl+C и BLOCKED, терминал возвращается в обычное
состояние. Только если процесс убит `kill -9`, область прокрутки остаётся: верни её `reset` или
`printf '\e[r'`.

**Размышления модели: начало текста и «Развернуть».** Под строкой размышления роли серым идут первые
300 символов текста, а длинный текст кончается словом «Развернуть»:

```
│   implementer │ 14:02:31 ▸ размышляет (1240 симв.)
│   implementer │          Сначала перечитаю промпт контроллера целиком: что от меня ждут, какие
│   implementer │          файлы мне разрешено менять и в каком формате вернуть ответ… Развернуть
```

Сколько символов видно сразу, задаёт `--thinking-chars <N>` у `run` и `resume` (или
`AGENTFLOW_THINKING_CHARS`), `0` — только строка «размышляет» и «Развернуть».

Клик по блоку раскрывает весь текст на месте, пометка меняется на `▾`, в конце текста — «Свернуть».
Строки лога ниже и панель стоят на месте, а строки выше уходят вверх, в историю терминала. Повторный
клик по блоку сворачивает его обратно к началу текста: лог под ним поднимается, и следующий вывод идёт
сразу под последней строкой. Если текст длиннее места над блоком, видно столько, сколько влезает, а
последняя строка — `… ещё N строк — целиком в events.jsonl`. Размышления, напечатанные до изменения
размера окна, не раскрываются.

**После прокрутки колесом.** Пролистанное окно iTerm2 остаётся в истории терминала, а клики над
историей iTerm2 программе не передаёт: обычный клик там ничего не раскрывает. Поэтому «Развернуть» ещё
и ссылка на файл с полным текстом (`.agentflow-runs/<run>/thinking/NNNN-<роль>.md`): ⌘-клик открывает
его и из истории. Обычный клик снова раскрывает на месте, когда окно прокручено до конца вниз.

На время `run` и `resume` терминал в режиме мыши:

- текст выделяется с ⌥ (Option) в iTerm2;
- первый щелчок колеса выключает перехват на секунду, дальше колесо листает историю как обычно. Через
  секунду после прокрутки клик по строке на экране снова раскрывает. В iTerm2 можно снять «Report mouse
  wheel events» (Profiles → Terminal), тогда колесо не перехватывается совсем;
- набранное во время прогона не отображается, Ctrl+Z и Ctrl+\ не действуют. Ctrl+C прерывает run, как
  обычно. На время диалога режим мыши выключается, меню и ввод работают как без него;
- `--no-mouse` или `AGENTFLOW_NO_MOUSE=1` выключают режим: строка `… размышляет (N симв.)` и начало
  текста, «Развернуть» — только ссылка на файл (⌘-клик). Без TTY (вывод в файл или pipe) режим не
  включается, ссылок нет.

После `kill -9` терминал остаётся в режиме мыши: верни его `reset` или
`printf '\e[?1000l\e[?1006l'; stty sane`.

Проверить клик без моделей: `npm run agentflow -- run tasks/01-slugify.md --mock --auto-approve --inject think-long:implementer`.
Пока первая сессия implementer 30 с присылает размышления, кликни по «Развернуть».

## 5. Петли конвейера

| Петля | Лимит | Где в коде |
| --- | --- | --- |
| уточнение intent → ответы человека | — | `stageClarify` |
| вопрос с вариантами → обсуждение с ролью → снова меню | `limits.discussTurns`, дальше диалог | `Human.question`, `discussFor` |
| артефакт: spec-author → валидация → snapshot → spec-reviewer, REVISE | 3 авто, дальше диалог | `artifactLoop`, `artifactExhausted` |
| твоё ревью артефакта: принять / вернуть / исправлю сам → снова ревью | человек | `artifactGate` |
| битый JSON / нарушение контракта → новый экземпляр ревьюера | 2 повтора, дальше диалог | `callReviewer`, `infraExhausted` |
| сквозное ревью → исправление артефактов → переревью downstream | 3 авто, дальше диалог | `holisticLoop`, `reaccept` |
| согласование и freeze: условия, вопросы, возврат артефакта | человек | `stageApproval`, `freezeProblems` |
| freeze: digest спеки, сверка перед каждым шагом apply | — | `stageFreeze`, `verifyFreeze` |
| гейты красные → тот же implementer | 3 попытки на вызов | `implementWithGates` |
| батч: реализация → гейты → коммит → ревью кода, REVISE (с 3-го раунда — новый implementer) | 3 авто, дальше диалог | `batchLoop`, `applyExhausted` |
| acceptance по замороженной спеке | — | `runAcceptance` |
| полные гейты → финальное ревью → исправления implementer / acceptance-tester | 2 авто, дальше диалог | `stageFinal`, `applyExhausted` |
| отчёт → приёмка → `openspec archive` | человек | `stageReport`, `stageHumanAcceptance`, `stageArchive` |
| простой сессии или серия отказов ACL → ждать / повторить шаг / стоп | порог policy, дальше диалог | `Watchdog`, `interventionHandler` |

`--inject all` включает точки: `review-bad-json`, `artifact-revise:proposal`, `holistic-revise`,
`gate-red:1`, `batch-revise:1`, `final-revise` (срабатывают один раз), `artifact-stuck:specs`,
`batch-stuck:2` (одна и та же находка все автоматические раунды — показывают диалог исчерпания) и
`stall:implementer` (первая сессия implementer молчит; под `--mock` порог простоя 2 с — сторож,
диалог вмешательства: ждать, затем повтор шага) и `discuss-question` (на первом вопросе с вариантами
автопилот задаёт реплику обсуждения, mock-роль отвечает и уточняет описание варианта), `discuss-dialog`
(в первом диалоге исчерпания автопилот задаёт реплику первой роли петли, затем выбирает
рекомендацию). Отдельно: `--inject proceed:<петля>` — в первом диалоге петли (`clarify`,
`artifact:<id>`, `holistic`, `batch:<id>`, `acceptance`, `final`) автопилот выбирает «Всё равно перейти
дальше» с причиной «fault injection»; `--inject blocked:<петля>` — первое ревью петли
(`artifact:<id>`, `holistic`, `batch:<id>`, `acceptance`, `final`) возвращает BLOCKED, открывается диалог
блокера; `--inject stall:<роль>` — то же для любой
роли, `--inject think-long:<роль>` — первая сессия роли 30 с присылает размышления раз в секунду
(проверка клика по ним, в `all` не входит), `--inject kill-after:<этап>` убивает контроллер после
этапа (проверка resume).

Блокер роли — вердикт BLOCKED ревьюера артефакта, сквозного ревью, батча или финала (в том числе
`needsHuman` в apply), BLOCKED acceptance-tester, повторённая находка security/behavior, которую автор
оспорил, ответ implementer `NEEDS_SPEC_CHANGE` — открывает диалог: дать недостающий контекст и повторить
шаг (текст уходит в уточнения intent), обсудить с ролями петли, остановить run, всё равно перейти
дальше. Рекомендуется остановка, поэтому `--auto-approve` останавливается, как раньше.

Сразу в BLOCKED, без диалога, run переводит только контроль целостности: изменена замороженная спека,
роль записала вне ACL или вызвала MCP вне allowlist, код изменился во время ревью, в change нет задач,
freeze невозможен; а также твой выбор «остановить» и решение без TTY. Причина — в `state.json` и
`ACCEPTANCE.md`.

## 6. Что где лежит

```text
AGENTS.md                    контекст для агента: карта, команды, соглашения, неочевидные факты, решения
.qwen/agents/*.md            пять ролей — единственный источник истины (model, effort, tools, maxTurns, промпт)
.qwen/settings.json          общие запреты для интерактивного qwen
.agentflow/policy.yaml       CLI, лимиты петель, ACL ролей, гейты, denyAll
.agentflow/rubrics/*.md      рубрики артефактов и ревью; обязательные checks — в разделе «Обязательные проверки»
.agentflow/review.schema.json  контракт ответа ревьюера
openspec/                    config.yaml (context/rules для артефактов), schemas/agentflow (spec-driven + test-plan),
                             specs/ — базовые спеки конвейера (7 capability), changes/
tools/agentflow/             controller.ts roles.ts config.ts context-builder.ts review-validator.ts
                             snapshot.ts gates.ts openspec.ts git.ts state.ts human.ts dialogs.ts inject.ts report.ts
                             log.ts status-panel.ts session-tracker.ts intervention.ts
                             agents.ts mock.ts smoke.ts agentflow.test.ts
                             run.sh — гейты демо-проекта; bin/agentflow.mjs, bin/agentflow-gate
src/ test/ e2e/              демо-библиотека, на которой решаются тестовые задачи
tasks/                       тестовые intent: 01-slugify, 02-parse-duration, 03-incomplete
.agentflow-runs/<run-id>/    manifest.yaml state.json events.jsonl contexts/ reviews/ gates/ evidence/
                             ACCEPTANCE.md worktree/ (ветка agentflow/<change>)
```

`events.jsonl` — полный журнал: каждое сообщение каждой SDK-сессии, решения ACL (у отказов —
`category` и `hint`), сводки отказов (`denials`), простои и вмешательства (`stall`, `acl-streak`,
`intervention`), гейты.
`contexts/` — промпт каждого вызова роли, diff батчей, отчёт acceptance.
Merge ветки — вне конвейера, после твоей приёмки (команды в конце `ACCEPTANCE.md`).

## 7. Отличия от документа

- Route моделей, `envKey` и `extra_body` не используются: модели берутся из `/model` корпоративного CLI,
  effort передаётся через `query({ effort })` (SDK 0.1.8), без доработки форка.
- В демо-проекте kit — схема `openspec/schemas/agentflow` (`spec-driven` плюс `test-plan`); в других репозиториях — их собственная схема.
- Запуск локальный: git worktree без контейнера, sandbox и сетевого allowlist. Fail-closed граница — ACL
  контроллера в `canUseTool` плюс сверка изменённых путей после каждой роли.
- Лимитов бюджета и времени нет (`roleTimeoutMinutes: 0`); расход пишется в `state.json` для информации.
  Зависшую сессию ловит сторож простоя (`limits.stallMinutes`) — решение за человеком, а не таймаут.
  Гейты, которые запускает сам контроллер, по времени не ограничены: их видно в панели с момента запуска.
- Гейты демо-проекта — `lint` (eslint), `unit` и `e2e` (`node --test`) в `run.sh`; другие репозитории задают свои в `gates.ops`.
- Хуки Qwen Code и MCP-источники требований не подключены.
- Спеку пишет spec-author, а не ты: ты ревьюишь каждый артефакт после PASS ревьюера и решаешь по
  исчерпанным раундам. Команды `/opsx:*`, `/spec-review`, `/spec-waive`, `/spec-approve` не нужны —
  те же решения принимаются в диалогах контроллера.
- GigaCode читает проектные настройки из `.gigacode/`, а не из `.qwen/`: запреты `.qwen/settings.json`
  для интерактивной сессии gigacode скопируй в `.gigacode/settings.json`. Контроллеру это не нужно —
  он сам читает `.qwen/agents/` и применяет ACL.
